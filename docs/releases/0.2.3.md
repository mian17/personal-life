## v0.2.3 — the repository can be public: no job of ours runs on the owner's host

**1 commit · 9 files · +448 / −262.** The count includes this file.

### What this release is

The change that makes publishing safe, not the publishing itself. Nothing in
`apps/`, `packages/` or `compose.yaml` moves: no image, migration, port, schema or
env-var name changes, and no application code is touched. What changes is CI
(one workflow deleted, one added), the secret-scan config, one `package.json`
script, RULE 7 in the architecture checker with its tests, and the two runbooks
that describe how this repository is operated.

### Removed

**`.github/workflows/sonarqube.yml` is deleted, and it was the last job of this
repository that ran on the owner's machine.** It was also the only workflow
naming a `self-hosted` runner: `runs-on: [self-hosted, sonarqube]`, the
`fedora-sonarqube` runner, on the same host as the SonarQube container so that
`http://127.0.0.1:9000` was reachable without exposing the instance. `runs-on`
belongs to the workflow and not to whoever triggered it, so the moment a stranger
can open a pull request, that job is a way to run a stranger's commit on the
owner's host — with its SSH keys, its other checkouts and its network — and a
green run's log shows nothing.

What that leaves behind, stated plainly:

- **No CI job runs on the owner's host any more.** `tests.yml`,
  `compose-boot.yml`, `backmerge.yml` and the new `secrets.yml` all name
  `ubuntu-latest`, which they already did; the deleted workflow was the only
  exception, so the repository now has no host-registered runner in its path.
- **The local SonarQube instance keeps its container, its stored analysis and its
  MCP consumers, and receives no CI scans.** The scan is run by hand now:
  `sonar-project.properties` is still the config and `SONAR_TOKEN` still comes
  from the container. `docs/runbooks/sonar-autofix.md` is corrected in the two
  places that claimed the workflow scanned `dev`.
- **The `sonar-autofix` webhook pipeline goes dormant until a scan is run by
  hand.** The receiver in `scripts/sonar-autofix/` is untouched, but a webhook
  fires on an analysis, and analyses arrive only when someone runs one. Nothing
  triggers it on a push to `dev` any more.
- **Pull-request analysis continues, unchanged, through the SonarCloud GitHub
  App.** That integration runs on Sonar's infrastructure: the check
  `SonarCloud Code Analysis` reported SUCCESS on #184, which targeted `dev`.

`sonar-project.properties` stays: it documents the exclusions, test paths and
coverage report paths the local scan reads, and deleting it would lose the only
copy of those.

### New

**A secret-scan gate reads the whole history, because the whole history is what
becomes public.** `.github/workflows/secrets.yml` (`Secrets`) runs on every pull
request to `dev` or `main`, every push to `dev`, and by hand. It checks out with
`fetch-depth: 0` — a key removed in a later commit is still in the history, so a
scan of the tip answers the wrong question — then runs gitleaks in the official
image pinned by digest, mounted read-only, with `--redact` so a leak never echoes
into a log anyone can read. Pinned by digest and not by tag because a tag can be
moved to a different image, and this step reads every byte of the repository.
Ten-minute ceiling, per-PR concurrency group like `tests.yml`.

**`.gitleaks.toml` extends the default rule set with exactly one allowlist
entry.** The finding it silences is `generic-api-key` at
`packages/crypto/test/envelope.test.ts:17`, key `92e11dcd...`: a published
NIST/CAVP AES-GCM known-answer vector mirrored from pyca/cryptography's
`gcmEncryptExtIV256.rsp`, test input rather than a credential, and the reason
travels in the file so a reader can check it against the citation above the
constant. It names that path and nothing else — a regex over the repository, or a
path wide enough to cover the code the key protects, would stop reporting the next
real finding.

**`npm run secrets` runs the same scan locally, with no host install.** Same
image digest, same config, `--redact`. It mounts the repository and its common git
directory read-only: this repository is worked in linked worktrees, where `.git`
is a file pointing outside the mount, and a scan that quietly found no repository
— 0 commits scanned, exit 0 — would be a gate that only looks like one.

**RULE 7 in `scripts/arch-check.mjs`: no workflow may name a `self-hosted`
runner.** It reads every `.yml` under `.github/workflows/`, judges every trigger
— `workflow_dispatch` included, since a job reachable by hand is still reachable,
and an allowlist of triggers is a second thing to get wrong — and ignores
comments, because "no self-hosted state" in a doc comment is the rule being
obeyed: `tests.yml` and `compose-boot.yml` both say it. The rule is whole-tree, so
it reports the file whoever added it. Proven able to fail rather than asserted
clean: one test plants a `self-hosted` runner under `pull_request` and one under
`workflow_dispatch`, both must be reported, and both are; a third test plants the
phrase in comments and must stay silent. `npm run test:arch` goes from 20 tests to
24.

**`docs/runbooks/public-repo.md` carries the checklist and the invariant.** The
runner is still registered at repository level (`fedora-sonarqube`) and must stay
unregistered — RULE 7 is the tripwire for the workflow half, and neither half
alone gets code onto the host. A merge is not a sandbox either: `npm ci`, the
build and the suites run wherever the branch is built, install scripts of
`better-sqlite3` and `argon2` included. The runbook also names the repository
setting that matters most on the first day a fork exists — Settings → Actions →
General → Fork pull request workflows → "Require approval for all outside
collaborators" — and the fact that `main` and `dev` have no required status
checks, so a red `Secrets` job is a thing to read, not a thing to assume.

### Verification

Only what was run here:

```
npm run test:arch   24 tests, 24 pass, 0 fail (was 20)                 exit 0
npm run arch:check  no findings                                        exit 0
npm run secrets     872 commits scanned, 17.76 MB, "no leaks found"    exit 0
same image, default rules only:
                    1 finding — generic-api-key
                    packages/crypto/test/envelope.test.ts:17           exit 1
```

The third line is the gate passing on this tree; the fourth is the same scan with
`.gitleaks.toml`'s allowlist removed, which is what makes the third line mean
something: exactly one finding in 872 commits, the known-answer vector, and
nothing else. The scan reports rule, file and line, and redacts the match.

### Upgrading

Nothing. No migration, no backup, no new env-var name, no port change, no data
directory change: the diff contains none of those, and no application code. A
deployment of this commit needs no more than the one before it.

One operational note: the owner's `fedora-sonarqube` runner is still registered
and the AGENTS-independent part of going public is unregistering it
(`gh api -X DELETE repos/mian17/personal-life/actions/runners/<id>`). Deleting the
workflow removed the only thing that used it; unregistering removes the access
itself, and `docs/runbooks/public-repo.md` says so in the place someone will look
before flipping the repository public.
