## v0.2.2 — CI now boots what ships, so the next dead env var fails before a release

**6 commits · 11 files · +2017 / −28.**

### What this release is

The promotion of `dev` to `main` for #179, #180, #181 and #182, on top of two
bookkeeping merges that keep `main` an ancestor of `dev`.

**It changes no application code.** All eleven touched files are CI and tooling
(`.github/workflows/tests.yml`, `.github/workflows/compose-boot.yml`,
`scripts/arch-check.mjs`, `scripts/arch-check.test.mjs`,
`scripts/ci-compose-env.sh`, `scripts/release.sh`), docs
(`docs/runbooks/compose-boot-ci.md`, `docs/runbooks/release.md`, `AGENTS.md`),
one `package.json` script entry (`release`), and `LICENSE`. No image, migration,
port, schema or env-var name changes. Nothing needs rebuilding.

Every change here answers one failure: v0.2.1 shipped three features dead —
`MEAL_TODOS_API_URL` and `FOCUS_TODOS_API_URL` were read with no fallback and
never forwarded to their containers, and the IdP refused to boot under
`NODE_ENV=production` for missing `OIDC_PRODUCER_*` callbacks. The test suites
were green throughout, because nothing in CI compared the code's requirements
with `compose.yaml`, and nothing in CI had ever run the deployment.

### Fixed

**A required env var that `compose.yaml` never forwards is now a failing rule.**
RULE 6 in `scripts/arch-check.mjs` reports every variable a service reads with no
fallback that is not a key in that service's own `environment:` block. It handles
both read shapes the code actually has: the dot form `process.env.NAME`, and the
bracket form through a resolved constant — `process.env[TODOS_API_URL_ENV]` at
`apps/meal-service/src/meal-todo.controller.ts:235` and
`process.env[FOCUS_TODOS_API_URL_ENV]` at
`apps/focus-service/src/todos/focus-todos.module.ts:15` — where the constant is
resolved at its declaration, including from `@life/service-kit`. A dot-only grep
misses both bracket sites, which is why the rule resolves constants instead of
matching text. The rule is topology-scoped like rules 3 and 4, not
diff-scoped: the subject is the deployed artifact, so a variable compose never
forwards is dead whichever branch dropped it. `NODE_ENV`,
`APP_DEV_SKIP_ACCESS_GATE` and `OWNER_LOGIN` are excluded with their reasons in
the source. The rule's own gap is stated rather than hidden: the IdP composes
`OIDC_PRODUCER_${name}_REDIRECT_URIS` at runtime, and no static read can see
that. `npm run arch:check` now runs in `tests.yml`'s `test` job, after Typecheck
and before the minutes-long coverage run. Proven able to fail: removing
`MEAL_TODOS_API_URL` reports `meal-todo.controller.ts:235`, removing
`FOCUS_TODOS_API_URL` reports the bracket-form site, and a read with a fallback
is not reported.

**A static read cannot see a name composed at runtime, so CI now builds and boots
the real stack.** `.github/workflows/compose-boot.yml` runs on every PR to `dev`
or `main` and on every push to `dev`: install, generate a throwaway env file,
validate with `docker compose config`, build the eight images, create the
bind-mount data directories, then `up -d --wait --wait-timeout 300`. It then
asserts each backend's own `/health/ready` **from inside its container** — that is
service-to-service reachability over the compose network, which a host-side curl
cannot show — plus the host-published endpoints, dumps `ps`, per-container health
status and 200 lines of logs per service on any outcome, and always tears down
with `down -v --remove-orphans`. Two prerequisites were needed and are now part
of the job: a fresh checkout has no `apps/*/data` because they are gitignored, so
Docker created each bind source as root while every image runs as uid 1000 and the
first real run died with `SqliteError: unable to open database file` on
focus-service and idp — the job creates the six directories and chowns them to
1000:1000 first. `scripts/ci-compose-env.sh` writes the env file compose reads:
fourteen variables, meaning every variable this stack is *required* to have at
boot, not merely every variable `docker compose config` requires at
interpolation. `config` accepts an empty `OIDC_APP_CLIENT_SECRET` and a missing
issuer; the IdP and the app then throw. That distinction is the entire reason the
job exists.

**With `OWNER_LOGIN` undefined, the boot job could only ever prove the access
gate.** Every request 403'd at `gate.ts` before the identity gate was reached, so
"the app answers something" was the most the job could assert. #180 writes a
throwaway `OWNER_LOGIN` into the CI env file and replays the header Tailscale
Serve would forward, which separates the two gates into three assertions: 403 on
`/` with no headers (ACCESS arms and fails closed — the correct answer, not a
defect), 307 on `/` with `x-forwarded-host` plus a matching
`tailscale-user-login` (ACCESS admits the owner, IDENTITY redirects an
unauthenticated visitor), and 200 on `/icon.svg` with the same headers (a public
path, served, so both gates genuinely said yes). The last one is `/icon.svg` and
not the favicon, and that is a finding: `apps/app/proxy.ts:66` drops
`favicon.ico` and `_next/*` from the matcher, so `decideGate` never runs on those
paths — `gate.ts`'s `PUBLIC_EXACT` entry for `/favicon.ico` is dead for the proxy
while the unit test still exercises it, so the unit suite could not catch the
trap. Asserting 307 there would have asserted that the gate decided when it had
not.

**Two passwords were base64, and base64 cannot go in a URL.** `FEEDBACK_DB_PASSWORD`
and `FEEDBACK_RABBITMQ_PASSWORD` are interpolated into `postgresql://` and
`amqp://` URLs, but were generated with `openssl rand -base64 32`. Base64's `/`
ends the URL's userinfo segment, so `new URL()` threw "Invalid URL" and
feedback-service could not boot from its own connection config. That is why the
compose-boot job passed one run and failed the next: 7 of 10 base64 samples carry
a `/` or a `+`. Both now use `openssl rand -hex 16`, the same shape
`scripts/setup-dev-env.sh` already uses on the real deploy path. The six
`*_MASTER_KEY` values stay base64 — `@life/crypto` consumes them as encoded keys
and they are never placed in a URL.

**A merged promotion was being treated as a release.** v0.2.1 shipped and the tag
was skipped, then had to be recovered by hand, because the procedure lived in a
conversation instead of the repo. `scripts/release.sh` (`npm run release -- <x>`)
now refuses unless five preconditions hold — clean tree, HEAD is `origin/dev` (or
`--ref`), the tag is new locally and on origin, `docs/releases/<x>.md` exists and
is non-blank, and every workflow on that exact SHA is `completed`/`success` — then
bumps `package.json`, creates an annotated tag carrying the notes, pushes the
commit and the tag, creates the GitHub release, and prints the three proofs
(local tag SHA, tag on origin, release URL). `--skip-ci-check` exists for a
release after a flake and prints the evidence it ignored; `--dry-run` writes
nothing but the one-line version bump. `docs/runbooks/release.md` carries the
notes house style and what the script deliberately does not decide. `AGENTS.md`
gains the matching "Releasing — a merged promotion is not a release" section, and
its tables were reformatted because the changed-file format gate inspects only
the files a PR touches; prose is unchanged.

**Two Sonar findings inside the new rule were fixed without changing what it
reports.** `javascript:S6353`: the value capture group in `NAMED_CONSTANT` was
`[A-Za-z0-9_]+`, which is exactly `\w`, so it became `\w` — the name group stays
`[A-Za-z_$][\w$]*`, which allows `$` and forbids a leading digit and is
therefore not `\w`. `javascript:S7776`: `NOT_SHIPPED` is a membership table, so
it is a `Set` and its call site uses `.has()` instead of `.includes()`. #181
reports `test:arch` still at 20/20 and a planted missing `MEAL_TODOS_API_URL`
still reported.

**The repository now carries the GNU GPL v3.** #182 adds `LICENSE`, the verbatim
GPL-3.0 text. No source file gains a header, and nothing in the build, the images
or the runtime changes.

The failure on `dd200d7` is the stale allowlist entry, verbatim from the log:

```
audit: FAILED
  stale entry      GHSA-gcqx-w48m-w2h4  deepmerge  low — npm audit no longer reports it; delete the exception
```

`npm audit` no longer reports that advisory, and `scripts/audit-gate.mjs` fails on
any entry the audit no longer reports — an exception that rots is worse than no
exception, because it hides the next one. So this PR deletes the entry; it does
not suppress anything. `.github/audit-allowlist.json` now reads
`"advisories": []` with its `comment` untouched, which is the only reason the
Tests job on `dd200d7` was red. Locally the gate is `UNVERIFIED-BY-RUN`: this
host's registry mirror (`https://registry.npmmirror.com`) answers 404 on
`/-/npm/v1/security/audits`, so `audit-gate.mjs` fail-closed on a missing audit
report before it compared anything. CI's verdict is that job's to give.

and `SonarQube` are green on the merge commit `2b660f5`, but that commit carries
no Tests run of its own — the green Tests run for #181 is the PR run on
`51b16df`, its branch head.

### Upgrading

Nothing. No migration, no backup, no new env-var name, no port change, no data
directory change — the promoted diff contains none of those. A deployment of this
commit needs no more than the one before it.

Two operational notes for whoever cuts the tag: the notes file has to be committed
before `npm run release -- 0.2.2` runs, because the script's first precondition is
a genuinely empty `git status --porcelain`; and the audit allowlist is now empty,
so the next high or critical advisory — of any package, dev dependencies included
— fails CI until someone adds a reviewed entry with a `reviewBy` date.
