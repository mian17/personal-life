# Spec: `notes-backfill` — plaintext → envelope migration

Module id: `notes-backfill` (see `MAP-data-privacy.md`). Depends on `notes-at-rest`.
Status: IMPLEMENTATION CONTRACT.

## Objective

One idempotent script that migrates existing content rows (`note.body`, `tag.name`)
to `enc.v1` envelopes, provisions `user_keys` per owner, and relocates the
`UQ_tag_name_owner` index to service enforcement. Human-run inside the deploy
window (AGENTS.md §8: production data migrations are planned and documented here,
but executed by the human).

## Behavior

Script: `apps/note-service/scripts/encrypt-backfill.ts` (run convention mirrors
`apps/idp/scripts/seed-user.ts`).

- **Idempotence by prefix detection:** rows already starting `enc.v1.` are skipped.
  Re-running is always safe; the report is stable.
- **Owner grouping:** rows group by `ownerSub`; `NULL` owner rows (legacy
  pre-boundary) use the sentinel owner `_legacy_` so nothing is ever left plaintext.
- **Key provisioning:** for each owner group without a `user_keys` row: generate DEK,
  wrap under `NOTE_MASTER_KEY`, insert. Existing rows are never rewrapped.
- **Encryption:** per row, AAD shapes from `SPEC-notes-at-rest.md` (note AAD binds the
  row's uuid; tag AAD binds owner+field). Batched, each batch in one transaction.
- **Schema:** `DROP INDEX IF EXISTS UQ_tag_name_owner` (service now enforces the
  invariant — see `SPEC-notes-at-rest.md`).
- **Modes:** `--dry-run` prints the planned counts (rows to encrypt, keys to create,
  index to drop) and touches nothing. Default mode applies and prints the same counts
  as a final report (encrypted / skipped / keys created / errors).
- **Failure:** a row that cannot be encrypted aborts the batch transaction and exits
  non-zero with the row id in the error — never a half-reported success.

## Deploy Checklist (human-run)

1. Stop the stack (`docker compose down`).
2. Backup: copy the note-service DB file to `<db>.pre-encrypt-<date>` (rollback path).
3. `NOTE_MASTER_KEY=<key> <run command> scripts/encrypt-backfill.ts --dry-run` → review counts.
4. Same command without `--dry-run`.
5. Boot (`docker compose up -d`), verify counts endpoint/UX (phone check).
6. Rollback if needed: stop, restore the backup file, boot.

Prod `NOTE_MASTER_KEY` is generated by the human (`openssl rand -base64 32`); it
never enters the repo (hard line: no secrets).

## Testing Strategy (temp DB fixtures only — `data/**` is a hard line)

1. Fixture of plaintext rows (2 owners + NULL owner + trash rows + duplicate-ish tag
   names) → run apply → every content column starts `enc.v1.`; `user_keys` rows exist
   for all owner groups incl. `_legacy_`.
2. Idempotence: run twice → second report shows all-skipped, zero keys created, and
   the ciphertext is byte-identical (no re-encryption).
3. Round-trip: `decryptField` with the provisioned DEK reproduces the original
   plaintext (note AAD binds the row uuid; tag AAD binds owner+field).
4. `--dry-run` on the same fixture changes nothing (DB bytes unchanged).
5. Failure path: a poisoned row (e.g. forced key error) aborts without partial writes.
6. Index relocation: post-run, the unique index is gone and service-level dedupe
   still prevents duplicate tag names (covered by `notes-at-rest` suite; asserted here
   for the migration half).

## Boundaries

- Always: idempotent, dry-run first, transactional batches, counts in the report.
- Ask first: any change to AAD shapes or envelope formats (they are cross-module contracts).
- Never: open `apps/note-service/data/**` from tests or tooling run by agents;
  invent key material in code; commit keys; partial-batch success reporting.

## Success Criteria

- All required tests green on temp fixtures; `npm run typecheck` clean.
- The deploy checklist is executable verbatim by the human.
- Re-runs are provably safe (idempotence test).
