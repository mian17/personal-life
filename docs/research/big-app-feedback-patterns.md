## 2. Form & category patterns

**Where the affordance lives.** Three stable families:

1. **In-product menu/toolbar** — VS Code's *Help → Report Issue*, Notion/Figma/Slack's help
   menus, Google's *Send feedback*. Lowest friction, and the entry point can **pre-fill
   context the user would otherwise type** (VS Code: version, platform, extension list,
   console errors).
2. **Persistent widget/bubble** — Sentry's Feedback Widget ("displayed anywhere in your
   application"), Intercom's Messenger. Always available, survives navigation, can be
   triggered *by* a failure (Sentry's Crash-Report Modal pops after an error).
3. **Detached surface** — Apple's Feedback Assistant app, public portals (Fider, Canny),
   GitHub's issue tracker reached from a menu. Zero UI intrusion, but the user leaves the
   product.

Our choice — a toolbar item in every app opening one dialog — is family 1, the pattern
with the most documented adoption (GitHub's issue forms, VS Code's Help menu, Google's
send-feedback).

**What forms actually collect.** Across the fetched forms the required core is small:
*what happened / what did you expect / reproduce it* (GitHub, Kubernetes, Sentry, VS Code).
Optional enrichment is context the machine already knows: version, environment, URL, tags,
screenshots, logs, replay (Sentry, GitHub, VS Code). The consistent lesson: **required
fields stay few and human; context fields are auto-attached, not typed.**

**Category taxonomies.** Three shapes dominate:

- **Fixed small enum, user-picked at submit:** GitHub's default issue types
  (`task`, `bug`, `feature`), VS Code's two templates, Sentry's bug/feature/flaky/support
  templates. Feature-request vs. enhancement are usually **not** split — they collapse into
  one "feature/request" bucket.
- **Type implied by *which form* was opened:** Kubernetes stamps `kind/bug` or
  `kind/feature` from the selected template rather than asking for a dropdown — fewer
  decisions for the reporter, no possible mismatch between form and label.
- **Type at capture, area as a second axis:** Sentry requires a **Product Area** dropdown
  alongside the bug/feature template — a *type × area* matrix, which is exactly
  "grouped by app, then type".

A fourth value (`question` / `support` / `other`) appears repeatedly as an *escape hatch
routed elsewhere*: GitHub suggests a `question` label, VS Code sends questions to Stack
Overflow, Sentry has a `support` template, Sentry's product-area list ends in
`Unknown`/`Other`. So the taxonomy question is less "how many types" than **"where does
non-actionable feedback go"**.

**Duplicates.** Handling is layered, never blocking:
GitHub suggests up to 3 similar issues inline and is explicit that suggestions are
*non-blocking*; VS Code asks users to search first and to use reactions instead of `+1`
comments (which doubles as a priority signal); Fider/Canny-class boards use **voting** so
duplicates become votes rather than new rows; PostHog collapses repeats *after* capture by
clustering open-text themes. Nobody I found rejected a submission as a duplicate at the
form.

## 3. Routing & triage

What happens after submit, from the fetched sources:

- **Straight into an issue tracker.** GitHub forms stamp labels/assignees/projects/type;
  Sentry can create or link a **GitHub/Jira issue** from the feedback row, and an alert can
  do it automatically for every new feedback; Kubernetes expects enhancements to leave the
  tracker for a KEP/SIG conversation; VS Code files against the right repository.
- **Into a dedicated inbox first, tracker second.** Sentry's *User Feedback page* is
  described as "similar to your e-mail inbox": chronological, unresolved-first, filterable
  by project / environment / date / search, with resolve, assign, spam. This is the closest
  published match to our `/feedback` inbox.
- **Into a board.** Fider/LogChimp/Canny-class portals collect posts and votes publicly.
- **Into a queue/channel.** PostHog pipes survey responses to **Slack and webhooks**;
  GitHub's own webhook guidance tells receivers to acknowledge fast and push the payload
  onto a queue (it names RabbitMQ as an example).
- **Routed by a human decision, not automation, for product judgment.** PostHog's scout
  explicitly "stops at the report and routes it to a human reviewer rather than starting a
  pull request", because *"survey finding is user sentiment, not a defect with a known fix."*

**Who triages.** Always an owning team, never a shared free-for-all: Sentry's Product Area
list is generated from a **product-owners** mapping; PostHog routes to "whoever owns that
survey"; VS Code has a documented triage/grooming workflow with automated triage; GitHub
lets maintainers assign/label at creation. Grouping-by-area and ownership are the same
mechanism wearing two hats.

## 4. Event / queue architecture patterns

### 4.1 The dual-write problem and the transactional outbox

Debezium's engineering write-up states the problem and the fix plainly: a service that
writes a business row *and* publishes a message to a broker cannot span both in one
transaction, so you get either a persisted row with no event or an event with no row.
Their answer — **write the event into an `outbox` table in the same transaction as the
business row**, then let an asynchronous process propagate it — is exactly our `feedback`
+ `feedback_event` plan.

Key quotes/properties from that source:

- "not only an `INSERT` into the `PurchaseOrder` table is done, but, **as part of the same
  transaction**, also a record representing the event to be sent is inserted into that
  outbox table."
- The outbox row carries `id` (uuid), `aggregatetype`, `aggregateid`, `type`, `payload`,
  where **`id` is "unique id of each message; can be used by consumers to detect any
  duplicate events, e.g. when restarting to read messages after a failure."**
- The event UUID is also propagated as a **message header**, "which allows for efficient
  duplicate detection by consumers, without having to examine the actual message contents."
- The consumer keeps a `MessageLog` table; `alreadyProcessed(eventId)` short-circuits
  re-deliveries, and the log write shares the consumer's transaction so a rollback keeps the
  message un-consumed. "This is to prevent any duplicate processing of events caused by the
  **'at least once' semantics** of this data pipeline."
- The event structure is **"part of the emitting service's API"** — consumers should be
  lenient and tolerate unknown attributes.

Two implementation flavours exist for *reading* the outbox: **log-based CDC** (Debezium
tails Postgres' WAL — "As opposed to any polling-based approach, event capture happens
with a very low overhead in near-realtime") or **application-level notification** (our
`pg_notify` + `LISTEN` dispatcher). The write side is identical; only the transport of
"something changed" differs. Our choice of NOTIFY keeps the same transactional guarantee
(Postgres delivers a notification only on commit) without a CDC connector.

### 4.2 Delivery guarantees on the broker

RabbitMQ's reliability guide is unambiguous:

- "Use of acknowledgements guarantees **at least once** delivery. Without acknowledgements,
  message loss is possible … and only **at most once** delivery is guaranteed."
- On the publisher side: retransmit anything not confirmed — "There is a possibility of
  message duplication here, because the broker might have sent a confirmation that never
  reached the producer … Therefore consumer applications will need to perform deduplication
  or handle incoming messages in an idempotent manner."
- On the consumer side: "It is recommended that consumer implementation is designed to be
  **idempotent** rather than to explicitly perform deduplication." The `redelivered` flag is
  only a *hint* (it may be unset on a message a consumer has already seen).
- Durability is a precondition: durable queues + messages published as `persistent`.

A RabbitMQ engineering post on at-least-once dead lettering shows the same guarantee being
*constructed* rather than assumed: without confirms, dead-lettered messages "may arrive…
[or] may get lost"; the at-least-once strategy forwards, waits for **all** publisher
confirmations, and only then acknowledges back to the source queue — at the cost of
buildup and extra CPU, which is why it is opt-in.

### 4.3 Idempotency keys on the wire

RabbitMQ Streams' deduplication post is the cleanest published statement of our
`event_id` rule: deduplication needs (a) a **producer name** reused across restarts and
(b) a **strictly increasing publishing ID**, usually the message's own identifier such as
"primary key for a database record". The broker filters publishes whose publishing ID is
≤ the last seen one, *while still confirming them to the client* — i.e. a retried submit
succeeds from the caller's view and produces exactly one stored event. It also notes that
consuming applications should still be idempotent.

GitHub's webhook best practices document the same idea for HTTP event delivery:
use the **`X-GitHub-Delivery`** header "to ensure that each delivery is unique per event"
(replay protection) — and note that a **redelivery keeps the original GUID**, so dedup keys
must be *event*-scoped, not *attempt*-scoped. Operational caveats from the same docs: the
receiver must answer within 10 s (hence "set up a queue to process webhook payloads
asynchronously"), failed deliveries are **not** auto-redelivered, and manual redelivery is
possible only for the past 3 days.

### 4.4 Ordering, replay, retention

- **Ordering per entity:** Debezium routes by `aggregateid` as the message key so all
  events for one aggregate land in one partition and are consumed "in the exact order as
  they were produced." Ordering is scoped to an entity, not global.
- **Replay:** "Durable logs also support re-playability, i.e. new consumers can be added as
  needed … without touching the source service." A consumer that starts late reads from
  the beginning. This is the explicit justification for our `feedback_event` change log
  with a `seq` cursor and replay on restart.
- **Retention:** topic retention is a deliberate business choice — Debezium discusses
  retention windows, tombstones vs. compaction, and moving historic events to cold storage,
  warning that deleting events ends replayability: *"when deleting events, the event stream
  will not be re-playable from its very beginning any longer."* RabbitMQ's dead-letter post
  adds the operational half: set `max-length`/`max-length-bytes` so unforwarded messages
  cannot grow without bound.

### 4.5 What the pattern is *nobody* claims

No source claims exactly-once delivery. The universally documented contract is
**at-least-once transport + idempotent consumer dedup on an event id** = exactly-once
*effect*.

## 5. Multi-app grouping (one capture form, one inbox)

Every fetched product solves "many surfaces, one funnel" the same way — **capture the
surface as an immutable field and group at read time**:

- **Sentry:** one widget API for every app; the feedback list is then *filtered and grouped
  by project, environment and date*, and the form itself carries a required **Product Area**
  dropdown generated from a product-owners map. Type (bug/feature) and area are independent
  axes, so `group by app, then type` is a two-pivot query over the same rows.
- **GitHub:** one "New issue" button per repo; type/labels/area are metadata stamped on
  creation; **Projects** views "group by a field" and, when you create an issue inside a
  group, the field is auto-set from the group. Grouping is a *view* over records, never a
  separate table.
- **PostHog:** one SDK renders every survey; each answer is an event carrying person
  properties and context, so grouping happens in analysis, not at submit.
- **LogChimp / Fider / Canny:** one portal, posts organised **by boards** — the board is the
  product area, exactly as our `app` id will be.
- **Atlassian JSM (†):** the inverse trade — many *forms* (request types) behind one portal
  when field sets genuinely differ. Relevant only if apps ever need different fields.

Implication: the `app` id must be captured on every row (our intent already does this),
owned by the server from the authenticated call context rather than chosen by the user —
Sentry's required user-picked Product Area is the weaker form of the same thing, because a
dropdown can be answered wrongly while a server-supplied app id cannot.

## 6. Privacy, retention and data boundaries

- **Owner/tenant boundary.** Sentry scopes everything by organization/project (feedback is
  listed per project, searchable per org) and warns when a field "will divulge your org slug
  publicly". GitHub's webhook guidance: never put secrets in the payload URL, use a signing
  secret, verify SSL, allow-list sender IPs. Our `principal.sub` on every row is the same
  boundary, applied per user instead of per tenant.
- **Auto-attached context is a privacy decision.** Sentry joins feedback to replays, URLs,
  tags and error context; PostHog attaches session replay and person properties to every
  answer. Both are defensible for an analytics product, and both are exactly what an
  owner-only personal-life app does *not* need by default. Keeping v1's payload to
  {type, description, app, principal} is the conservative end of the observed range.
- **Third-party processing must be declared.** Sentry documents that its spam-classifying
  LLM is "internal to Google Cloud Platform and no data is stored or persisted", names the
  sub-processor, and offers an opt-out toggle. The lesson is procedural: any enrichment we
  add later (an LLM triage step is the obvious one) needs a documented data flow and an
  off switch — today we add none.
- **Non-public disclosure routing.** Kubernetes' bug form diverts security issues to a
  private channel. Not applicable while we are the only user, but worth keeping as a
  documented rule if the service ever accepts outside submissions.
- **Retention.** The event log is the replay source, so retention and replayability are the
  same policy: Debezium warns that pruning the log forfeits replay from the beginning;
  RabbitMQ requires a length cap so buffers stay bounded. Concrete reading for us: never
  prune `feedback_event` below the cursor of a live consumer, and record any future
  retention decision as a spec line rather than an implicit housekeeping job.
- **Encryption at rest.** None of the fetched product docs mandates encrypting feedback
  content at rest (Sentry and GitHub document transit/integrity controls instead). Our
  `enc.v1.` envelope at rest comes from this repo's Contract 2, not from industry
  feedback-product practice — i.e. **stricter than the observed norm**, deliberately.

## 7. What this implies for our design

Confirmed decisions are quoted from `docs/intent/feedback-service.md`. Each recommendation
is tagged **matches** or **diverges** against the evidence above.

1. **Keep exactly three types — `feature request` / `enhancement` / `bug report`.**
   *Matches.* GitHub ships three default issue types, Kubernetes ships two (`kind/bug`,
   `kind/feature`), VS Code two templates; no fetched product splits feature-request from
   enhancement as separate user-facing choices. **Divergence, accept it:** common practice
   adds a `question`/`support` escape hatch (GitHub `question` label, VS Code → Stack
   Overflow, Sentry `support` template). Cheapest fix later: a fourth type or a help link —
   do not fold questions into the three types now.

2. **Required description stays required and is the only required human field.**
   *Matches.* GitHub `validations.required`, Kubernetes requires three narrative fields,
   Sentry requires problem/repro. **Add type-specific guidance, not fields:** pre-fill the
   textarea's help text by type ("steps / expected / actual" for bugs, "problem / why it
   matters" for features) — this is what Sentry's *distinct templates* and Kubernetes's two
   forms achieve, without breaking "one shared form".

3. **`app` is captured on every row and derived from the calling context, not user-chosen.**
   *Matches intent* (`each app passes its app id`) *and is better than the norm:* Sentry
   makes **Product Area a required dropdown the reporter fills in**, which can be wrong;
   VS Code pre-fills environment data instead. Maintain an explicit app-id registry
   (Sentry's product-area list is generated from a product-owners mapping) so grouping by
   app can later map to an owner without schema change.

4. **Automatically attach machine context the user shouldn't type.** *Matches the pattern,
   beyond our current scope.* VS Code pre-fills version/platform/extensions/console errors;
   Sentry attaches URL/tags; GitHub forms stamp labels/assignees/projects from metadata.
   Recommendation: include app id, app version/route and submission timestamp in the row
   and in the `feedback.submitted` payload — cheap, and it is the field every reviewed
   form ends up asking for. Screenshots/attachments stay out of v1 (our explicit out of
   scope), which is a **documented divergence** from Sentry/GitHub/VS Code.

5. **Client idempotency key generated *before* the request, `UNIQUE`; `event_id`
   `UNIQUE`.** *Matches.* Debezium's outbox `id` ("detect any duplicate events, e.g. when
   restarting"), GitHub's `X-GitHub-Delivery` (unique per event, **same GUID on
   redelivery**, so dedup must be event-scoped not attempt-scoped), and RabbitMQ Streams'
   publishing ID (broker still *confirms* a duplicate rather than erroring). Note the
   UX detail this buys: a retried submit should return success, as RabbitMQ's dedup does.

6. **At-least-once everywhere; consumer dedups on `event_id`. Exactly-once *effect*, never
   promised as delivery.** *Matches, and matches the literature exactly.* RabbitMQ:
   acks ⇒ at-least-once, publisher retransmits on missing confirms ⇒ duplicates; Debezium:
   consumer `MessageLog.alreadyProcessed(eventId)` guards against "the 'at least once'
   semantics of this data pipeline". Also matches RabbitMQ's explicit recommendation that
   consumers be *idempotent* rather than hand-rolled dedup — our `event_id` check is the
   idempotency rule, so prefer it over broker-side dedup (a Streams-style filter is an
   optional extra, not a replacement).

7. **Transactional outbox + `pg_notify` push is the right shape; treat NOTIFY as a
   wake-up signal, not as the log.** *Matches* Debezium's "same transaction" write side.
   **Divergence (deliberate):** Debezium/Debezium read the outbox via **CDC on the
   transaction log**; we read it via an `AFTER INSERT` trigger + `pg_notify` + `LISTEN`
   dispatcher. Consequence to write into the spec: Postgres notifications are transient
   (not persisted for a disconnected listener) and payload-limited, so **the dispatcher's
   recovery path must re-read `feedback_event WHERE dispatched_at IS NULL` / `seq > cursor`
   after any reconnect, lost notification or overflow** — the table, never the
   notification, is the source of truth. *(inference from NOTIFY semantics; verify against
   the Postgres `NOTIFY` docs before the spec hard-codes limits — source listed below was
   not fetchable here.)*

8. **RabbitMQ with durable exchange, persistent messages, publisher confirms.**
   *Matches* the reliability guide's checklist (durable queues + persistent messages +
   confirms ⇒ at-least-once). Add the operational half GitHub documents: **fail fast to the
   caller, hand off to a queue** (GitHub tells receivers to answer within 10 s and names
   RabbitMQ as the queue), and expose a **recovery/redeliver path with bounded history** —
   GitHub keeps only 3 days of deliveries and does *not* auto-redeliver. Our `seq` cursor
   replay is that path; recommend surfacing "undispatched count / cursor lag" so a stuck
   dispatcher is visible rather than silent.

9. **Publish an ordered, replayable event log and keep it ordered by `seq`; scope ordering
   to the aggregate.** *Matches.* Debezium: a new consumer can "process the topic from the
   very beginning", ordering is per aggregate (partition key = `aggregateid`), and the event
   shape is an API consumers must tolerate evolving. Recommendation: version the
   `feedback.submitted` payload and write "unknown fields must be ignored by consumers" into
   the consumer contract.

10. **Owner-only inbox grouped by app, then type; newest-unresolved first; filters, not
    new tables.** *Matches.* Sentry's inbox is "chronologically-organized with the most
    recent, unresolved feedback at the top", filterable by project/environment/date; GitHub
    Projects groups by field over plain records; LogChimp organises posts by boards. Our
    grouping must be a view over `app` + `type` — no denormalised group column, no separate
    per-app tables. Ordering-by-app-first mirrors how every reviewed product lets you pivot
    by area first.

11. **No public board, no voting, no upvotes in v1.** *Diverges from Canny/Fider/LogChimp
    and from VS Code's reaction-driven prioritisation* — but all of those exist to arbitrate
    *many external requesters*. With a single owner, votes are a coin flip; skip it (YAGNI).
    Revisit if a second requester ever appears, at which point the Canny shape (post + vote +
    status) is the documented template.

12. **No third-party enrichment in v1 — no LLM categorisation, spam filtering or
    auto-clustering — and `enc.v1.` at rest plus `principal.sub` scope stay as-is.**
    *Diverges from Sentry (AI summaries, LLM spam detection) and PostHog (theme
    clustering), both of which exist because of volume; and is stricter than the observed
    norm* (§6) — Sentry/GitHub document transit and integrity controls, not content
    encryption. Their explicit framing is the guide: PostHog's scout "stops at the report
    and routes it to a human reviewer", because the judgment is human. At one owner,
    manual grouping by app/type *is* the triage. If volume later demands it, the documented
    pattern is clustering at the **analysis** layer (PostHog) or clickable generated
    categories (Sentry) — never changing the stored row — and any LLM step needs a
    documented data flow and an off switch (Sentry's own sub-processor disclosure).
